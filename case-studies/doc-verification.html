From Four Identical Cards to One

Designing a booking-level document verification system at Breeze.

Executive Summary

A booking-level Additional Documents page that deduplicates Timatic API requirements across travelers in a booking, gating international check-in until acknowledgment.

The prior design produced four identical acknowledgment cards for a family of four flying to the Dominican Republic. The shipped version collapses them to one.

Shipped in MR 5613, currently in pre-prod review.

Role:

UX/UI Designer

Duration:

~2 months, 5 working sessions

Responsibilities:

UX research, system design, prototyping, validation testing

The Problem

Three Layers of Complexity

International check-in surfaces document requirements from Timatic, an industry travel API. The challenge wasn't surfacing them. It was making sense of what came back.

1. API Ambiguity

Timatic AutoCheck v1.3 returns per-pax results with five evaluationResult values (YES, NO, CONDITIONAL, UNKNOWN, transient retry) across multiple RuleSet codes (REQDOC, REQFRM, REQVIS, REQTIX, REQYF, VALDOC, plus INF* informational).

Not every code maps to UI. Not every result is actionable. There's no metadata to tell you whether a form is "per-family" or "per-person."

2. Per-Traveler vs Booking-Level Structure

The original flow nested documents inside a per-traveler wizard, producing duplicate cards. The engineering manager flagged it directly:

3. Mixed Scope Within One Booking

A US/Ukraine couple flying to DR generates one shared e-ticket card and one Ukraine-only authorization card. The UI has to communicate "this applies to everyone" vs "this applies only to Olena" without making the everyone case feel skippable.

The System

A Vault-Based Working Surface

This project ran on a structured vault: project files, atomic reasoning notes, dated session logs, and a live JSX prototype sandbox served the work. Five sessions captured. Seven design decisions extracted into individual reasoning files. The system shows itself through the decisions below.

Where AI led: pattern recognition across 29 Timatic scenarios, rapid variant generation in the sandbox, reasoning extraction from rationale docs, typography audit, convention codification.

Where AI didn't: stakeholder framing, knowing when to stop iterating, the pre-prod routing bug catch, and the Figma source-of-truth spec.

The Decisions

Four Calls That Shaped the System

Decision 1: Booking-Level Page, Not Per-Traveler Step

Decision: lift document acknowledgment out of the per-traveler check-in wizard and into a booking-level page.

Alternative: keep documents inside the per-traveler wizard.

Evidence: a family of four flying to DR was generating four identical REQFRM cards. The EM call confirmed it as a real friction point, not a hypothetical edge case.

AI's role: enumerated the dedup edge cases (mixed nationality, partial overlap, all-shared, all-unique) and helped write the dedup algorithm spec.

PNR Shape Old (per-traveler) New (booking-level)
Family of 4 → DR 4 identical REQFRM cards 1 card
US/Ukraine couple → DR 2 e-ticket cards + 1 Ukraine card 1 shared e-ticket + 1 Ukraine card

Decision 2: Text-Match Deduplication on code + rawText

Decision: dedupe results by hashing on the rule code plus the raw response text. If two travelers' responses match exactly, collapse them into a single card.

Alternatives: ask Timatic for per-family vs per-person metadata (it doesn't exist), or hard-code per-code policy.

Evidence: the per-family vs per-person distinction is irrelevant if you can observe directly whether multiple travelers got identical results. Dedup at the text level sidesteps the missing metadata problem entirely.

AI's role: ran the 29 scenarios through the proposed dedup logic to surface collisions. Engineering later shifted the dedup key to title + description (backend pre-maps codes to titles). Behavior preserved, implementation cleaner.

Decision 3: Show Only REQFRM, REQVIS CONDITIONAL with URL, and REQTIX

Decision: display only three response types in the acknowledgment UI. Skip everything else.

Alternative: show all CONDITIONAL responses; let guests sort signal from noise.

Evidence:

  • REQVIS YES is satisfied (skip)
  • REQVIS NO blocks at boarding pass issuance (skip, agent handles)
  • REQVIS CONDITIONAL without a URL is a simple exemption (skip)
  • VALDOC, REQDOC, REQYF, INF* are out of scope by code

AI's role: built the URL-detection regex (/https?:\/\//) as the single discriminator for actionable REQVIS CONDITIONAL cases, and compressed the policy table into a working spec.

Decision 4: Shape Asymmetry, Not Color, for "Applies To" Scope

Decision: distinguish "applies to all travelers" from "applies to a named traveler" using shape and icon, not color saturation.

Alternative: the original Figma, a gray pill for "all travelers" + sky-blue pill for named traveler.

Evidence: a 5-second scan test (n=20) on the original gray-pill design returned 70% comprehension, below the 80% threshold I'd set for shipping. The stakeholder skippability concern was validated, not speculative.

AI's role: 12+ variants iterated in the live sandbox in a single session (variants A through N covering Moxy badge color pairs, eyebrow text in five colors, colored-icon hybrids, asymmetric treatments). Variant N landed: gray eyebrow text with UsersIcon for "All Travelers" + Moxy pill-stroke sky-blue per named traveler.

Research Evidence

Three Streams of Validation

Discovery

29 Timatic Scenarios

API-level discovery across nationalities and routes (CUN, PUJ, NAS, SJO). Documented in research-timatic-results.md. Drove the dedup algorithm and the show/skip policy table.

MVP Testing

11 Participants, March 2026

Surfaced 7 critical dev issues (Android camera permission, scanner crashes, nationality reset, back-button loop, doc-link round-trip break, false confirmations, save failures) and 8 UX issues (instructive scanner errors, "see agent" with no reason, multi-pax structure, blocked early).

Comprehension

5-Second Scan Test, n=20

70% accuracy on the original gray-pill design, below the 80% threshold. Validated the skippability concern as real, not speculative. Drove Decision 4.

The Handoff

Figma as Source of Truth, JSX as Working Surface

The Figma spec served as the engineering source of truth. JSX prototypes (responsibility-cards-2026-03-31.jsx, responsibility-cards-2026-04-09.jsx) and a live Vite sandbox were iteration surfaces: fast to throw away, useful for variant exploration. Once variant N stabilized, decisions translated to Figma for handoff.

MR 5613 shipped most of the spec with a handful of accepted small deviations:

  • Page title renamed to "Additional Travel Requirements"
  • Domain-only link button
  • Single primary footer button
  • Collapsed acknowledged row drops the traveler name
  • Card divider added

One known divergence: the tag treatment shipped as the original Figma version, not variant N, because Figma wasn't updated before implementation kicked off. Documented in design rationale Section 14. A pattern worth naming (see learnings below).

What I Learned

Four Patterns I'm Carrying Forward

1. Lock Design Decisions Into Figma Before Implementation Kicks Off

Once engineering builds, the leverage to course-correct shrinks. JSX prototypes are working surfaces, not source of truth. When a test invalidates a Figma version, update Figma before handoff, not after.

2. Surface UX Gaps as Routing Problems, Not Code Reviews

"I'd expect to be able to return to it" lands harder than "the setShowButton condition is wrong." The pre-prod Complete Later → Manage Trip dead-end was caught as a guest-experience gap, not a code review note.

3. Stay In Role

Calling out implementation details (e.g., the clear() wiping partial acks) reads as out-of-role. Better: ask the UX expectation question and let engineering answer with what they know.

4. Conventions Earn Their Keep

The typography audit during this project surfaced off-scale sizes (11/13/15/18px) leaking into the prototype. Drove the expansion of the team's typography conventions, including a grep-before-shipping audit step.

Coda

Where AI Ended and Design Judgment Began

  • AI iterated 12 tag variants in a session. The decision to stop at variant N and run a second scan test was a design judgment call.
  • AI compressed the Timatic policy table. The decision to skip Bahamas C17 ("Items to declare") because it would confuse guests was a domain call.
  • AI flagged the dedup edge cases. The decision to invest in the booking-level architecture rather than patch the per-traveler flow was a structural call backed by EM input.
  • The pre-prod routing bug was caught by walking the flow as a guest, not by reading code.
